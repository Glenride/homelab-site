The Key That Couldn't Pay

by D'Vaughn House

The morning was supposed to end with a one-dollar license sold on Base. Instead, the safest key in the room turned out to be the one that could not pay at all — and that failure, proved live, was the most useful thing that happened all day.

The morning's plan

Monday, November 9, started with a clean plan. The morning work block, ten to noon, was checkout plus the agent end to end: one real license, one dollar, settled on Base through the multi-party signing service.

By 10:12, a limited key had been added on-chain for the demo account: it could call one method, sign, on the signer contract, and spend at most one NEAR. It was also the key that could not pay.

One yocto

The problem was the deposit, not the key's permissions. Every live sign call needs a deposit of one yoctoNEAR, the smallest possible amount. What nobody had verified, until that morning, was whether a limited key is even allowed to attach a deposit to its call.

It is not. The live test, run between 11:10 and 11:20, failed with the protocol's own answer: DepositWithFunctionCall. A function-call key cannot attach any deposit at all — not a large one, not one yoctoNEAR. The hole was in the protocol, not in our code: the limited key could never complete a live sign call.

The deposit is a compile-time constant — one yoctoNEAR — because the signer runs version 3.17.0 and the view that used to report it was removed in version 2.

So the careful key was set aside, still on-chain, still unused, and the app's key was swapped to the account's FullAccess key, which already lived on the same machine; the account holds 1.32 NEAR. A live test sign with the full key succeeded, on a dummy payload only — no Base transaction, no license recorded.

The page that forgot its own token

While the key was being sorted out, the checkout broke in a way that looked like user error. The quote request came back with "CSRF token mismatch." It was not. The page template had no CSRF-token meta tag in it at all, so the checkout code read an empty token and sent an empty header, and the server rejected it with a 419. The tests had never caught it, because the test suite bypasses that check entirely. The bug was in the app, not in anything the buyer did.

The fix was one line: the missing tag, added to the template, the cached views cleared, and the token verified rendering live on the checkout page. The tests stayed green, fourteen out of fourteen — tests that had never submitted a real quote through a real browser page.

The wrong rail, then the right quote

The first license of the morning, created about 11:20, was quoted on the wrong rail entirely: NEAR instead of Base, 0.279 wNEAR to a NEAR deposit address. It was left unpaid to expire on November 12. No money moved, and the relayer's nonce stayed at zero.

The next two licenses, the Base ones, stuck differently. They sat pending with no deposit address, because the quote service answered 400: "tokenIn is not valid." The interface was sending the origin asset in its erc20 form; the live quote service only accepts the nep141 form.

The fix was a small normalizer added to the quote request, translating the asset's label from one form to the other. The first retry still failed — the running queue workers still had the old code loaded — but after the workers were restarted both quotes succeeded, at 1.012526 USDC each. Pay the third license only; the second was a duplicate. Nothing had been paid as of 11:43.

Before any of that, the buyer had swapped $1.20 of ETH to USDC inside his chat wallet, which then held 1.475991 USDC on Base; the checkout's Base option is USDC only, not ETH.

Seamless, or nothing

That was the moment the brief changed, at 11:42, in his words. He said that for a NEAR build the flow needs to be seamless, that he had never been told it would be multiple steps, and that the goalpost had moved after he had been told it was possible. The multi-step flow had never been disclosed to him upfront. His decision: build the seamless version first, and let the demo video wait.

Seamless means exactly what it sounds like: connect a wallet on the page, click Buy, approve once. No copied deposit address, no separate swap, no second app. The work order written that morning was frontend-only, built on the injected wallet in the browser, for MetaMask and Coinbase Wallet — no new wallet-connect service, no new accounts, no new project IDs — and there would be no live paid purchase, on his call.

One more wrinkle: the chat wallet holding his USDC cannot connect to websites at all. Before the seamless demo can be recorded, his USDC plus a little ETH for gas has to move to MetaMask or Coinbase Wallet. Moving money is his step, and his alone.

The commit that closed the loop

The seamless checkout was built that same afternoon and verified independently: the wallet library pinned, a new wallet helper written, the checkout page doing Connect, then Buy, then Pay with the exact quote amount. Tests fourteen of fourteen, contract tests four of four, build clean. A click-through produced a live quote, license number four, again at 1.012526 USDC. No payment was broadcast; the deposit balance and the relayer nonce stayed at zero.

The next evening, November 10, at 23:05, that work went to the main branch as commit 7528818. Checking it caught one more gap: the settlement script had been left untracked, so a fresh copy would have had a broken settle path. A second order that night committed that script — 458 lines — as e9ef020, verified tracked on the main branch. The settle path is whole now.

The dollar lands

Five days later, November 14, the dollar landed. His 1.012526 USDC payment completed the swap leg — one dollar out, $0.007726 refunded — and License #18 settled on Base. The receipt came back clean, the license-recorded and scholar-credited events verified on-chain, the proof hash matching the record.

It did not land cleanly. The page stuck on "signing": the swap service returns hashes as objects, not strings, and the watcher crashed; then the settler found no node. Both were fixed live — a flattener for the hashes, the node binary pinned by path — the worker stopped so the settler's five-attempt counter froze at three. Attempt four succeeded.

The fixes are not committed yet: the proof is on-chain, the code still uncommitted. The key that could not pay taught us what the protocol allows. Saturday taught us: the dollar can land. It did.
