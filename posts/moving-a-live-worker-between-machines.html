Moving a Live Worker Between Machines Without Dropping the Queue

by D'Vaughn House

One queue, one worker, one move — and the watchers came along too.

I run a small worker that chews through a queue of tasks all day: it picks up the next job, runs it against a model, and records the result. For a while it lived on a small hosted box. Then, on October 27, I moved it to a machine in my own house. Nothing was lost, nothing ran twice, and the queue came out the other side exactly as it went in. This is how the move went, and the one rule it taught me that I will not forget.

Why the old box had to go cold

The old box never rebooted. That sounds like stability, but it was not. The platform it ran on pauses the box's network after a stretch of idle time, by design. So the worker would go quiet, get resumed, run for a while, and go quiet again. On October 26 it cycled 17 times. On October 27 it cycled 24 times.

Here is the part that made the decision simple. The box itself was contributing almost nothing. The worker's models already came through a proxy on the second machine, and the queue already lived in a separate database in the cloud. The box was just a place to host the daemon, the background process that watches the queue and runs the work.

That is also why two daemons sharing one queue would be a disaster. If two workers both watch a single list of jobs, both can grab the same job, or one can mark a job done while the other is still working on it. One queue means one daemon. So the move had a hard rule from the start: the old daemon had to be fully stopped and disabled before the new one started, and it had to stay off afterward. The old box would become cold standby — present, but never running the worker again.

Match the environment before the first task runs

Do not rush the new machine live and sort out the differences later. If the new machine runs the work even slightly differently, the first task it picks up becomes an experiment.

So the first step was not the move at all. It was matching. The live code was synced to the new machine fresh — not a stale copy, not a best-guess rebuild — and the new machine's runtime was matched to the old one's, library for library, so the code would behave the same way in its new home.

The model path needed no change, since the worker was already reaching its models through the proxy on the second machine. And the queue needed no migration at all, because it already lived in the cloud database — the reviews waiting in it would survive the move untouched, because they were never on the old box.

The cutover, step by step

A move like this is only safe if the order is right. Here is the order I used on October 27, on my own call:

Wait for an empty moment. The old daemon was stopped and disabled while no job was actively running. Nothing was mid-task, so nothing could be orphaned.

Sync the live code. The working code the old daemon had been running was copied to the new machine, as it stood.

Match the runtime, then start the service. With the code in place and the runtime matched, the new worker was enabled as a service on the new machine, set to start on its own and stay running. Its heartbeat — the regular signal that says "I am alive and watching the queue" — came back fresh within a minute of starting.

Confirm the queue. Then the check that mattered most: the queue counts on the new machine against the counts from before the move. They were identical — 18 done, 27 failed, 28 reviews pending. Same numbers, same list. Only then was the move done.

Leave the old box cold. The old daemon stays disabled. That last step is not a cleanup detail; it is the whole point. If the old daemon ever gets re-enabled, two daemons share one queue again, and everything the careful ordering bought is gone.

The rule the move taught: migrate the watchers too

Here is the part I got wrong at first. After the worker moved, two things that had watched the old box were still running: an idle watchdog that checked on the box, and a keepalive hook that fired a handoff every time the box flapped. Both were still pointed at the old location, watching a machine that no longer ran anything. Left alone, they would have kept flagging the worker as inactive and sounding alarms about a box that was supposed to be quiet.

At first I treated switching them off as a separate question, something to ask about after the move. That was the mistake. The move was not finished while its watchers still pointed at the old place. So, on my decision that same evening, both were switched off as part of the same move — not deleted, so they could be brought back if ever needed, but disabled, with nothing queued and nothing running. The lesson is now a standing rule in my house: when you move software off broken infrastructure, the move includes everything related to that broken piece. Its watchers, monitors, hooks, and scheduled checks go with it, disabled or removed in the same move. You do not leave orphaned watchers pointing at the old location, and you do not ask separately about them. The decision to migrate already covers them.

Verdict

The move worked because the groundwork was already there: the models came through a proxy elsewhere, the queue lived in a database elsewhere, and the old box was only ever a daemon host. The actual work was discipline, not heroics — stop on an empty queue, sync the live code, match the runtime, verify the heartbeat, confirm the queue counts, and leave the old daemon off, watchers included.

Who should copy this: anyone with a worker running on a box that keeps flapping, where the queue and the models already live somewhere else. Check what the box actually contributes before you move. If the answer is "just a place to run the daemon," the move is mostly ordering and verification. Get the order right, prove the queue survived with the counts, and take the watchers with you.
