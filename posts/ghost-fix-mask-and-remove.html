The Ghost Fix: Mask It, Then Remove It

by D'Vaughn House

Disable told it to stay down. It came back anyway. So I made it unable to start, then I took away the thing it was serving.

I fixed this exact bug once. Then it came back. That is the short version. The longer version is the fix itself, and the fix is why this piece exists. The hunt already has its own piece. This one is about what ended it.

Disable sounded final

On October 24, the stale connector on the old box got stopped and disabled. The site went stable. That looked done. It was not done.

On October 27, the diagnosis came back at 5:32 in the evening. Same stale connector, back from the dead. It had been running again since 5:08 in the morning UTC on October 25. Process ID 23106. Its config had never changed. It still pointed the blog at the old box on port 2368. It still had no rule for the dashboard. Anything it grabbed for the dashboard came back a catch-all 404.

It was also serving a stale copy of the blog. Seven posts. The newest was from October 21. The current day's post was absent entirely. The edge spread requests across the current connector and the stale one. A request that landed on the current host got the live blog. A request that landed on the old box got a 404 where the article should have been. Same address, two answers, no pattern you could see from one load.

Disable sounds final. It is a polite request. A disabled service skips boot. A trigger can still wake it up. Something on that box woke it up. I still do not know what.

The fix had two parts

I got the go-ahead at 5:33 that evening. The words were plain. Apply the fix. Stop, mask, and remove the stale Ghost.

The tunnel in question carries the ID 330198c8-d5ff-44fc-b354-dc66635fe7df. Two connectors claimed it. One was current. One was stale. The fix had to end the stale one for good.

Part one was the service. Stop it. Disable it. Then mask it. Masking is the stronger version of disabling. Masking points the service at nothing. It cannot start at boot. It cannot start from a trigger either. There is nothing there to start.

Part two was the container. Stop the stale blog container. Remove it entirely. The container was the stale site itself. Seven old posts, sitting there, ready to serve. As long as it existed, any connector that woke up had something stale to hand out. The rollback had to go.

The mask fought back

The mask did not land on the first try. It failed. The real unit file was still in place, and it blocked the symlink the mask needed. So I moved the real unit file aside first. Then the mask went through clean.

After that, the checks read the way they should. The service showed masked. It showed inactive. The symlink pointed at nothing. That is the whole point of masking. Disable leaves a service sitting there, waiting for a reason to run. Masking leaves it with nowhere to run from.

Take away the rollback

Then the container went. Docker stop, then docker remove. The stale blog container was gone from the box.

I had kept that container as a rollback when the blog moved to its current host on October 22. Sensible at the time. Careful, even. But a rollback is only safe if nothing can reach it. The stale connector could reach it. The edge could reach the stale connector. So the rollback was a live stale site with a road straight to it. Keeping it meant keeping the bug one trigger away from coming back.

The box got checked right after. No cloudflared process running. Nothing listening on port 2368. Service masked and inactive. The old host could not answer anymore.

Prove it stayed dead

The fix got verified the boring way. Twenty rounds across three addresses. The article. The dashboard login page. The dashboard front page. Every round came back 200. No flapping. The checks ran from 5:36 to 5:40 that evening, over several minutes.

The shape of the test matters here. Four clean loads prove nothing against a bug like this. Four loads can all land on the good connector by luck. That is luck with a good story. Twenty rounds across every address the tunnel serves, over minutes, gives the bug time to show up. It did not show up.

One wrinkle showed up instead. Right after the fix, the Cloudflare side still listed three stale box connections. That was inventory lagging behind reality. The probes said clean. The box said clean. I trusted the probes and the box, and they were right.

What I still do not know

What woke the disabled service on October 25 is still open. No timer was found on the old box. No scheduled job was found either. A review of its logs is still open.

Masking means that service cannot wake again through that path. The trigger itself is a separate question, and it stays open. Fixed and explained are two different words. This one is fixed. It is not fully explained. I will not pretend otherwise.

The rule

A move is done when the old host cannot answer anymore. Stopped, disabled, masked, removed. That is four steps, and the first two were not enough. I learned that twice on the same bug. A leftover is a live thing. Treat it like one, or it will come back and prove it.
