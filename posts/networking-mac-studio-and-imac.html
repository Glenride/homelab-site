What broke when I networked my Mac Studio and iMac together

by D'Vaughn House

Two machines, one network, five days of breakage — and a link that finally holds.

The goal

One machine runs the models. The other machine runs the always-on work and talks to it. The Mac Studio is the engine room; the iMac is the box that never sleeps. The earlier posts on this site left this link as a to-do. Here is the rest of the story — everything that broke between "two machines on the same network" and a link that actually works.

Hardware and cost

  • Mac Studio, M2 Ultra, 64GB of unified memory — the model server
  • 2017 27" iMac (iMac18,3), Omarchy / Arch Linux — the always-on homelab server
  • Both already owned. Operating cost is $0 a month; the only money in this build is the domain, about $12 a year.

Software stack

  • LM Studio — serves models over the network through an OpenAI-compatible API
  • Ollama 0.40.9 — lightweight model runner, part of the regular rotation
  • Tailscale 1.104.1 — the private network between the machines (macOS 26.5.2 on the Studio)
  • Tailscale Serve — exposes the Studio's model server to the tailnet only
  • socat — a small TCP proxy on the iMac, added later as the stable route

The machines on the network: the Studio at 192.168.1.187 on the LAN and 100.70.123.107 on the tailnet (mac-studio.tail22a20c.ts.net); the iMac at 192.168.1.191 on Wi-Fi, 192.168.1.148 on Ethernet, and 100.81.149.115 on the tailnet.

What broke and how it was fixed

I couldn't find the Studio's IP. The first problem was embarrassingly basic — my actual question was "how do i find the studio lan ip." The answer: Option-click the Wi-Fi icon on the Studio, or System Settings → Wi-Fi → Details. It reported 192.168.1.187, and that went into the config.

The port was wrong. I had 1234 in the config because that's LM Studio's default. The Studio said otherwise — "it says 1235 not 1234." So the endpoint became http://192.168.1.187:1235/v1, verified in my own terminal.

The server was only talking to itself. Then the reachability failure: the iMac still couldn't see the server. The diagnosis was that LM Studio was bound to localhost only — serving to itself, not the network. I confirmed it at the socket level: the listener was LM Studio's server process, bound to 127.0.0.1 only. It never listened on any network interface.

The setting that never took effect. The old advice was "enable Serve on local network" on the Server tab. My version has no Server tab at all — just a settings menu. One of the earlier posts on this site still says the LAN serving has to be enabled on LM Studio's Server tab; that line is stale, and this piece supersedes it — there is no Server tab in my version, and the checkbox it describes doesn't exist. The setting itself sits in Developer → Server Settings, but it never took effect for the running server: after a restart the listener came back on 127.0.0.1, and the record is that the toggle was still off in effect. My own research pointed at LM Link instead, the mesh-networking route: end-to-end encrypted, nothing public. I never set LM Link up. The working route was the command line: lms server start --bind 0.0.0.0 --port 1235. Even that fought me at first — the CLI command timed out waiting for the daemon while the GUI-run server kept running, bound to localhost.

The firewall was a red herring. My call at the time was "it's the firewall," and it was half right. macOS Firewall was enabled with stealth mode on, which explains the symptom — connections timing out instead of refusing, system pings dying. But stealth shapes the symptom; the loopback binding was the wall. Turning the firewall off alone would not have fixed anything.

The pings lied. System ping to the Studio's tailnet address returned 100% loss even while the tunnel was fine — macOS drops ICMP. The real test was Tailscale's own ping: pong via the LAN in 6ms, direct path. When a ping says a machine is dead, check with the tool that owns the network before believing it.

Tailscale, then Serve. On October 20 the Studio joined the tailnet, and the first bridge that actually worked was Tailscale Serve: tailscale serve --bg http://localhost:1235 on the Studio, which proxies the loopback-only server out to the tailnet and nowhere else. The iMac pulled the Studio's model list through it — five models, end to end. A five-day reachability saga, closed.

Then the Studio went down and the whole stack moved. On October 22 the Studio went offline twice. The first time, around 13:58, it crashed under LLM memory load and came back around 15:27. The second time was a kernel panic at 20:58, and it stayed down about fourteen hours. It came back when I got to it, and I applied the pending OS updates. After the updates, LM Studio was dark while Ollama answered fine on its own port. Same machine, same network, one service up and the other down: the fault was inside LM Studio, not the network.

The VPN started flapping. That same day the Tailscale VPN profile on the Studio got stuck looping "configuring and connecting," and the node kept dropping off the tailnet. The catch-22: on macOS the Tailscale VPN configuration is the connection — turning the VPN off disconnects the app by design. The loop stopped on its own and the node held across the next checks. The fix on record if it comes back is to quit Tailscale fully first, then remove the configuration, relaunch, and let it build a fresh one — with connect-on-demand left off.

The binding came back. After the OS update, the server was loopback-bound again — the listener was back on 127.0.0.1, and a restart through the GUI recreated it the same way. The fix that stuck was the CLI, on the new port: lms server start --port 1234 --bind 0.0.0.0. One wrinkle: the CLI tracks its server separately from the GUI's — lms server stop reported "not running" while the GUI's server was still listening locally. Verified from the iMac right after: the model list answered on the LAN and the tailnet with six models, and all four chat models served real completions in 83 seconds including model load time. Note the port moved in the process: the GUI server had served on 1235; the CLI server runs on 1234, and everything downstream moved to 1234 with it.

Serve died with the GUI server. That same afternoon, Tailscale Serve started returning 502 while the raw server answered fine on port 1234. Serve was still proxying the retired GUI server at localhost:1235. The fix was one command on the Studio: tailscale serve --bg http://127.0.0.1:1234. Verified from the iMac and the agent box — model list 200, live completion through Serve.

The direct route died, so the iMac became the bridge. On October 23 the wider fleet — OpenClaw, GT, the keep-warm script — moved off the Serve address to the direct tailnet address, after Serve stayed down. The InstaBox harness followed on October 24, rewired to the direct address on my tap. That night the box-to-Studio tailnet route died anyway: packets out, nothing back, while the Studio answered the iMac over the LAN in 6ms. So I built a proxy on the iMac — a small service listening on the tailnet at 100.81.149.115:12345 and forwarding to the Studio's LAN address at 192.168.1.187:1234. The iMac has a proven direct LAN path to the Studio and the box reaches the iMac reliably, so the proxy routes around the dead leg entirely. Verified from the box: model list in 0.25 seconds, seven models, live completion. The direct route healed on its own the next morning, and I switched the harness to the proxy anyway — the direct route stays as the fallback. The steward, OpenClaw, and GT stayed on the LAN/direct path.

The Studio sleeps, and nothing recovers on its own. The thread through all of this: when the Studio goes down, nothing comes back by itself. The fourteen-hour outage ended when I walked over to it. Two different failures, though. The overnight sleep that started it all was an accidentally triggered hot corner — I had one set to sleep the Studio — and I fixed that one myself on October 22, changing the hot corner from Sleep to Lock Screen. The fourteen-hour outage itself wasn't sleep at all: the panic log shows the machine never slept, it froze. The Energy setting and the pmset command are a different story — the setting was suggested on October 21, the pmset command given on October 22 and again on October 24, and there is still no confirmation either was ever applied. That part is still open. The model server died twice on October 24 — fixed the first time around 18:08 with the same CLI command, dead again by 20:28. For the second death the restart was prescribed, not confirmed run, and the port was still down at 21:48. The server was verified serving again that night by a lean model load on my tap at 22:05, with sanity completions coming back "LEAN OK".

Verdict

Networking two machines is three things: the right IP, the right port, and the server actually bound to the network instead of localhost. Check all three before you blame the model. When the software's UI changes out from under the guides, believe the software, not the guides — and when the GUI won't do what you need, the CLI will. Keep a second path: one route will die on you, usually at night, usually right after an update. And if your model server lives on a machine that sleeps, fix the sleep first, because every other fix you make will quietly unmake itself overnight.

Who should copy this: anyone with a strong machine and an old machine who wants one model server for the whole house. Run the heavy models where the memory is, run the agents where the uptime is, and don't trust a green "Connected" badge — verify with a real request from the machine that actually needs the answer.
