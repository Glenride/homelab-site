Docker on the iMac: what's running and why

by D'Vaughn House

One old desktop, now the always-on box for the whole operation — here's everything actually running on it in Docker, and what's still missing from the picture.

The one-sentence version

A 2017 iMac running Arch Linux is the production host for the whole operation: the public websites, the blog, and the dashboards — all of it in Docker containers, all of it reachable from the internet through a Cloudflare Tunnel with no port forwarding. The self-hosted tools run in containers too, and they mostly stay on the LAN and the tailnet — they don't face the public internet, with one exception: the password vault, which has its own public subdomain.

This is a snapshot of what's actually running on that machine, as of the last verified inventory in late October 2026. Not a wishlist, not a plan — the containers that were up, tested, and answering when someone checked.

How it got here

The iMac started as a desktop that fought its own install. By early October it had Arch Linux, working WiFi and Ethernet, SSH, and Docker verified with a hello-world run. The turning point came on October 11, when the ThinkTank OS stack went live behind a Cloudflare Tunnel and the iMac stopped being a project machine and became a production host: the Laravel app, Postgres, Redis, Horizon, and nginx, serving the main site and the store, verified live with a 200 response.

By the morning of October 22, the count already stood at fifteen containers — that was the tally at 11:15, before the evening's install added six more.

Eleven days later, on October 22, a second wave landed: the self-hosted starter stack — a homepage dashboard, an alert service, a job monitor, a page-change watcher, a password vault, and a file-sync service — all six containers up and verified on localhost, the LAN, and the tailnet in the same session.

The blog moved in on October 22. The Workshop dashboard followed. A system map for Glenride went live on October 25. And the machine that was once a repurposed all-in-one was the always-on box everything depends on.

The public sites

These are the containers the outside world actually touches.

ThinkTank OS — the main site and the store. The Laravel app (PHP 8.4) with Postgres, Redis, Horizon, and nginx. It serves the main site and the store subdomain through the tunnel. This is the stack that went live on October 11, and it's the reason the iMac has to stay awake: when this stack is down, the public sites are down. Most outages so far have traced to the box behind the tunnel, not the tunnel itself — with one exception: on October 24 a stale tunnel connector on the InstaBox split traffic on the shared ghost-blog tunnel and flapped Grand Central, while the blog itself stayed up through it.

The Dispatch — the blog. A single Ghost container (ghost:alpine) with SQLite, plus its own tunnel connector. It moved to the iMac from its old host on October 22, and the public checks passed twice that night: home, posts, images, and the admin panel all answering. It is the simple setup — one container, one database file, no separate database server.

The Workshop — the homelab command dashboard. This one has a history, and it's worth telling straight. The Workshop started as a host service on port 8791, not a container. A container twin was added the same day it was built, October 22, because the iMac's firewall blocks container-to-host-IP traffic and the tunnel needed a container to reach. Then the twin started crash-looping — restarting over and over with a segfault — while the host service kept answering fine. On October 25, at about 02:02 in the morning, the twin was stopped as redundant. That broke the public Workshop: the tunnel ingress still pointed at a hostname that existed only as a host systemd service, and the tunnel's Docker DNS couldn't resolve it, so the site answered 502. A replacement container went in that same evening at 21:21 — built on python:3.12-slim, chosen over Alpine because the Alpine image segfaulted on a basic network import — and the Workshop came back. The host service stayed for tailnet and LAN access.

Glenride System Map. A Flask app in a single container on port 8090, live at its own subdomain since October 25. It's the interactive org chart and operating-structure map for Glenride — departments, budget cycle, money flow, governance — with editable cards backed by a database file.

The self-hosted tools

These don't face the public. They face the household — the person running the operation.

Nginx Proxy Manager. The reverse proxy for the self-hosted apps. It got a patched rebuild during the October 23 certificate incident (more on that below), and it's the piece that decides which internal service answers which local address.

Homepage. The dashboard — one page with links to everything else. It runs on port 3000 and was one of the six containers verified on October 22.

Vaultwarden. The password vault, on port 8081, live at its own subdomain since October 23. One open item from that day's check: signups were still allowed on the public vault, which is the kind of thing you close the moment your own account exists.

ntfy. The alert service, on port 8086, with a write-only alerts topic for homelab notifications. It's how the machine taps its owner on the shoulder.

Healthchecks. The job monitor, on port 8008. It watches the scheduled work — the morning and evening sweeps, the Monday digest, the weekday job scraper — and notices when one of them doesn't check in.

changedetection. The page-change watcher, on port 5000. It watches pages and says something when they change. It also got a patched rebuild during the October 23 certificate incident.

Syncthing. The file-sync service, on port 8384, set up to sync with the Mac Studio — the pairing accept on the Studio side was still his pending step at install time, and no confirmation is on record. It's the quiet one — it's meant to move files between the two machines so nothing lives in only one place.

The apps and the bots

D'Quizz and InspireWrite. Two more Laravel apps in their own containers — the quiz app and the Bible reader app. Both were rebuilt during the October 23 certificate incident and verified live afterward.

The bots. Three bot containers were confirmed running and re-verified on October 23: the trading bot, the community-manager bot, and the Prism bot. They run alongside everything else on the same host.

The one that isn't on a Docker network

Grand Central — the terminal-style dashboard on port 8001 — is a host-networked container, not a bridge-networked one. This matters more than it sounds. On October 24, an attempt to move it onto the main tunnel failed for exactly this reason: the tunnel connector runs on a Docker bridge network, and bridge-network containers can't reach a host-networked service on an unpublished port. The move was reverted the same night. Grand Central stays where it is, on its own host-networked tunnel connector, until its deployment changes. If you ever wonder why Grand Central stays on the blog's tunnel instead of the main one, this is why.

The day the certificates broke

On October 23, a certificate-authority incident forced a rebuild of half the stack. A compromised certificate bundle meant containers that trusted the wrong certificates had to be rebuilt on fresh base images and re-tested from inside — each one probed to confirm it now rejected the bad endpoint instead of connecting to it.

The ThinkTank app and Horizon were rebuilt on a fresh PHP image and the whole stack recreated. The quiz app and the Bible app were recreated on rebuilt images. The homepage and the alert service were recreated on fresh images. The page-change watcher and the proxy manager got durable patched builds so the fix would survive the next rebuild. The trading bot, the job monitor, the Prism bot, the community-manager bot, the Workshop twin, and the blog were already patched and re-verified.

One container image was pulled fresh and deliberately not started: Paperless, the document manager. It's on the shelf, not on the box. That's the honest state of it — available, not running.

The iMac host itself is still waiting on its own fix, a system package update that needs his one manual step. The host and the containers are separate patients, and only the containers got treated that day.

What "running" means here

Every container named above was verified running on a specific date — seen up, answering requests, or tested from inside during the October 22 install, the October 22 migration, the October 23 incident response, or the October 25 verifications, when the System Map went live and the replacement Workshop container was added. Nothing in this guide is a container that was planned, drafted, or installed somewhere else and assumed to be here.

But a snapshot is a snapshot. The count was fifteen containers on October 22, and the inventory changed on October 23 and 25 — containers rebuilt on the 23rd, one stopped and one added on the 25th. There is no single complete container listing on record after those changes. What's listed at the end is exactly what's missing to turn this snapshot into a current inventory.

The shape of it

Step back and the pattern is simple. One old computer, one Docker host, three kinds of work: public sites the world sees, tools the household uses, and apps and bots that do jobs in the background. Two tunnels in front of it all, no open ports: one for the blog and Grand Central, one for everything else — a one-tunnel consolidation was tried on October 24 and reverted the same night. And one rule that has held through most outages so far — when something goes down, check the box before the tunnel. Usually the box is the problem. Once, it was a stale tunnel connector.

What's still missing

These are the records that would make this guide complete and current. Nothing here is invented to fill the space.

  1. No single current container listing. I have no complete docker ps output after October 25. The October 22 count was fifteen containers; the October 23 incident list names the containers that were tested, but it is a test list, not a full inventory. A current listing would confirm which containers are still running, which stopped, and whether anything new appeared.
  2. The bots' exact jobs are not documented in my notes. The trading bot, the community-manager bot, and the Prism bot were confirmed running on October 23, but my notes don't state in one place what each bot does day to day. Their roles will come from my own records, not from their names.
  3. Port numbers are on record for only some containers. The Tier 1 stack ports (Homepage :3000, ntfy :8086, Healthchecks :8008, changedetection :5000, Vaultwarden :8081, Syncthing :8384), Ghost (:2368), the Workshop (:8791), the System Map (:8090), Grand Central (:8001), the quiz app (dquizz-app :8000), the Bible app (bible-app :3000 — the container's own port, reached through the tunnel by service name, not a host-published port), and ThinkTank's web service (:80) are recorded. Port numbers for the ThinkTank stack's internal services (Postgres, Redis, Horizon) and the three bots aren't in my notes.
  4. Compose files and container names are not fully on record. My notes name some containers (thinktank-os-app-1, horizon, dquizz-app, bible-app, the-workshop-web, the-workshop, glenride-system-map, the-dispatch-ghost) but don't give a complete container-name list or the compose files that define the stacks.
  5. Resource use is only partly on record. Two host figures exist: 145G of disk free on October 22, and a load of about 1.1 after the October 24 reboot. But no per-container CPU or memory figures appear in my notes, so any claim about how hard any single container works would be invented.
  6. The Mac Studio is out of scope for this guide. Docker on the Studio is a separate, blocked story (Hub pulls fail on the locked macOS keychain), and the Studio runs its model server natively, not in Docker. It belongs in its own piece, not this one.
  7. Paperless is pulled but not running. The image was pulled fresh on October 23 and deliberately not started. Whether it gets installed, and when, is my call — this guide should not present it as part of the running stack until it is.
